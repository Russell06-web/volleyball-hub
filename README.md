## 這是什麼

一個以 React + Vite 打造的純前端原型，示範一個「排球專項」活動平台從探索、報名到主辦管理的完整互動流程。目標使用者是想找排球活動的玩家，以及想開團、招募隊友的主辦方——不是泛用運動平台，所以搜尋、篩選與活動資料都圍繞排球本身的實際需求設計（球制、網高、場地材質、位置缺人狀況等），而不是把排球硬塞進一個通用「活動報名系統」的樣板裡。

**沒有後端、沒有資料庫、沒有正式帳號系統**——所有資料都存在瀏覽器的 localStorage 裡，用來模擬「這個帳號的資料」，但實際上不是真的帳號。清除瀏覽器資料或換一台裝置，這些紀錄就會消失。

## 核心問題與核心任務

排球揪團最常卡住的地方不是「找不到活動」，而是找到活動之後才發現條件對不上：程度限制含糊、場地資訊不全、明明缺兩個舉球卻要等進去問主辦方才知道。這個原型針對幾個具體任務設計：

1. **依真正會影響能不能上場的條件篩選活動**——不只是類型跟城市，而是網高、球制、場地材質、位置缺人、單人／揪團限制。
2. **在決定報名前就看到關鍵資訊有沒有齊全**，而不是進了群組才發現主辦方沒寫地址。
3. **個人報名時能表達位置偏好**，即使系統誠實地說明這只是偏好，不是保證。
4. **重複比較多場活動**，尤其是條件相近、但網高或位置需求不同的場次。
5. **保存常用的搜尋條件**，下次不用重新設定一次類型／城市／程度。

## 技術棧

React 18・React Router・Vite・純 CSS（無 UI framework）・GitHub Pages（含 SPA fallback）・localStorage（模擬資料層）・Vitest（純邏輯與部分整合測試）

## 開發

```bash
npm install
npm run dev       # 本機開發伺服器
npm run build     # 產出 dist/，並自動複製 404.html 供 GitHub Pages SPA fallback 使用
npm run preview   # 本機預覽 build 結果
npm run lint      # ESLint
npm run test      # Vitest
```

`vite.config.js` 的 `base: '/volleyball-hub/'` 與 `App.jsx` 的 `BrowserRouter basename={import.meta.env.BASE_URL}` 對應 GitHub Pages 的部署路徑，兩者需要保持一致；`npm run build` 會把 `dist/index.html` 複製成 `dist/404.html`，讓 GitHub Pages 在使用者直接訪問或重新整理任何子路由時，仍能正確交給 React Router 處理，而不是顯示 404。

## 功能總覽

### 探索與篩選
- 真正運作的多關鍵字搜尋（標題／類型／場館／城市／地址／主辦方／程度／風格），搜尋框輸入時不會邊打邊把文字修剪掉或洗掉網址（見下方「搜尋框」）
- **兩層篩選**：基本條件（類型／性別／程度／價格／城市／日期範圍）常駐可見；排球專項的進階條件（位置需求／活動風格／網高／球制／場地材質／是否需要輪轉／可否單人加入／提供設備／是否包含程度或性別「不限」的活動）預設收合在「進階排球條件」裡（Progressive Disclosure），手機上則是「基本條件／排球條件／場地與設備」三段式手風琴
- 篩選是**硬性**的——選了程度、性別，資料上標示「不限」的活動預設不會被當成自動符合；要看到「不限」的活動，需要另外打開「含未限制程度」「含未限制性別」開關，而不是被系統偷偷放寬
- 搜尋、篩選、排序都同步到網址列，並驗證每個參數的合法值；不合法或多餘的參數會自動清除，重新整理、上一頁、下一頁、分享網址都能正確還原
- 從 Explore 進入活動詳情、再返回時，完整保留原本的搜尋與篩選狀態；如果是從「我的收藏」或「瀏覽歷史」點進來，返回也會回到那一頁，而不是一律回到 Explore
- **搜尋框**：畫面上顯示的是你正在打的原始文字（含前後空白），實際送進網址列與篩選邏輯的值只在打字停頓、按 Enter、或欄位失焦時才提交——輸入「台北 中階」中間打到一半不會被提前修剪成「台北中階」
- 找不到符合條件的活動時，不會只丟出一句「沒有結果」——系統會即時計算「如果放寬這個條件會多幾筆結果」，最多列出 3 個真的有效的建議（例如「顯示所有價格範圍的活動・12 場」），點下去立即套用；每個建議都經過真實計算，不是憑空建議

### 活動詳情與位置缺人
- 活動詳情頁顯示網高、球制、場地材質、是否需要輪轉、是否允許自由球員、提供的設備、以及一個簡化的場地位置圖，標示哪些位置目前缺人——圖示旁一定有對應的文字清單（螢幕閱讀器不需要依賴圖形），並清楚註明這是主辦方填寫的示範資料，不是即時名單
- 條件比對（符合目前條件／部分符合／需要確認）只出現在活動詳情頁，不在活動卡片上重複顯示（見 [docs/PRODUCT_DECISIONS.md](docs/PRODUCT_DECISIONS.md)）
- **報名前重點資訊摘要**：報名前就能看到程度、性別限制、網高、球制、位置缺口、剩餘名額、費用、付款方式與資訊完整度，每一項都標示「✓ 已明確」「! 請確認」或「資訊未提供」，不需要展開好幾層才看得到關鍵資訊
- **資訊完整度**提示：只在活動資料不完整時出現，且不是分數或百分比——只有缺地址、時間、程度、聯絡方式這類真的會影響判斷的欄位才會被標示為「重要」，缺技能說明、設備這類細節不會被誇大成風險

### 報名與快速加入
- 個人／揪團報名，含防止重複報名、重複候補、隊伍人數上限驗證；個人報名可以選擇希望參加的位置（不保證，僅供主辦方參考）
- **快速加入**：在個人資料設定常用姓名、示範電話、常用位置後，活動詳情頁的主要按鈕會變成「快速加入」，跳出確認視窗（不是自動送出）讓你在同一個畫面看到活動摘要、報名資料與付款方式，按下確認才會真的報名；沒設定完整時，按鈕會開啟完整報名表單。快速加入呼叫的是跟一般報名**完全相同**的驗證與寫入邏輯，不會繞過重複報名、候補、人數上限等規則
- 候補名單、取消與退款政策說明
- 主辦方可以**取消**已有人報名的活動（保留紀錄）或**刪除**沒有任何報名的示範活動——兩者都用自訂 dialog 確認，不使用瀏覽器原生 `window.confirm`

### 比較與收藏
- 最多同時比較 3 場活動：桌面版是完整比較表（活動可個別移除、收藏、連到詳情），手機版改成活動切換分頁＋逐項卡片，不會把 3 欄硬塞進 320px 螢幕
- 已取消或已結束的活動仍可以留在比較列表裡（顯示其狀態，不提供報名按鈕），可以個別移除
- 收藏活動、瀏覽歷史

### 已儲存的探索條件
- Explore 有任何篩選條件時可以「儲存這組條件」，最多儲存 5 組；只儲存篩選組合與排序，**不會儲存搜尋文字**，也**不會發送任何通知**——這點在儲存與列表畫面都會明確寫出來
- 個人資料頁可以套用、重新命名、刪除已儲存的條件

### 主辦方管理
- 建立活動的精靈流程分 4 步：基本資訊 → 場地與時間 → 排球規則與需求 → 費用與預覽，涵蓋球制、網高、場地材質、是否需要輪轉、允許自由球員、位置需求（可個別新增/移除）、提供設備、單人加入規則（關閉時必須說明報名方式）
- 表單驗證包含標題長度、人數上限、費用非負、位置需求人數不超過人數上限、活動日期不早於今天，重要欄位錯誤會顯示在欄位旁並自動把焦點移到第一個錯誤欄位，不是只跳一個 Toast
- 發布前預覽會顯示資訊完整度狀態；只有缺少核心欄位（地址、時間、程度、聯絡方式）才會擋下發布，缺少非核心細節只會顯示提醒，仍可以發布

### 個人資料
- 分成「我的活動」（我的報名／收藏活動／我主辦的活動／活動比較，各自顯示目前數量）、「我的排球偏好」（常用位置／常用程度／常用城市／快速加入設定／已儲存的探索條件）、「關於與支援」（隱私與資料說明／關於此原型／技術限制／語言／重置示範資料）三個區塊
- 刻意**沒有**付款方式管理、信用卡、交易紀錄、密碼、雙重驗證、登入裝置管理、安全中心、真正的帳號刪除、或假的通知中心——這些入口在設計階段就被移除，而不是用樣式藏起來（見 [docs/PRODUCT_LIMITATIONS.md](docs/PRODUCT_LIMITATIONS.md)）

### 其他
- 加入行事曆（.ics 下載）、Web Share API 分享
- 統一的 Toast 提示，不使用 `alert()`；所有互動視窗（報名、快速加入、儲存條件等）共用同一套 Sheet／Dialog 元件，具備 focus trap、Escape 關閉、背景捲動鎖定、開啟時自動把焦點移入視窗、關閉時把焦點還給觸發它的元素

## localStorage 架構

所有「後端資料」都存在瀏覽器的 localStorage 裡，用固定 key 分開儲存（活動、報名、收藏、瀏覽歷史、篩選偏好、個人資料、活動比較清單、已儲存的探索條件），並具備版本化 migration（`src/services/storageMigration.js`，目前版本 4）——升級後舊格式資料會自動轉換成新結構，缺少的欄位會補上安全預設值，完全無法辨識的資料會安全地回退到種子資料，不會讓畫面白屏。核心商業邏輯（報名驗證、活動狀態判斷、位置缺人計算、資訊完整度判斷、篩選/排序/搜尋、可替代篩選建議）都寫成不依賴 React 的純函式（`src/utils/*.js`、`src/services/*.js`），React Context 只是在外面包一層 localStorage 讀寫與 Toast 提示。

## 測試

專案**沒有**引入 React Testing Library 或任何大型 E2E 框架——這是刻意的技術判斷，不是省略：核心商業邏輯已經抽成不依賴 React 的純函式，Vitest 可以直接測試這些函式的輸入輸出，涵蓋率遠比重新渲染整個元件樹更直接；而元件之間的實際互動（點擊、表單送出、路由切換、focus 管理）在開發過程中透過真正的 headless Chrome（Chrome DevTools Protocol）跑過完整流程驗證，包括故意在多個裝置寬度下檢查有沒有橫向捲動、以及對每個路由做過白畫面/console error 掃描。

```bash
npm run test
```

涵蓋範圍包括（詳細清單見各 `*.test.js`）：搜尋與多關鍵字比對、探索頁網址參數解析與驗證、篩選邏輯（含 16 個維度）、活動狀態判斷（含時區邊界）、返回導覽狀態保留、debounce 邏輯、快速加入資格判斷、位置缺人摘要計算、活動比較清單驗證、已儲存探索條件驗證、資訊完整度判斷、可替代篩選建議（含「套用建議後結果數真的變多」的驗證）、localStorage migration。

## Future Roadmap

**Phase 1（已完成）** — 活動探索、搜尋、篩選、收藏、報名、候補與活動管理的前端原型。

**Phase 1.5（已完成）** — 排球專項資料模型與 IA（位置缺人、快速加入、活動比較、已儲存探索條件、資訊完整度、可替代篩選建議、4 步驟建立活動精靈）。

**Phase 3** — 線上付款、退款、交易紀錄、推播與 Email 通知服務（包含讓「已儲存的探索條件」真正發送新活動通知）。

**Phase 4** — 主辦方身分驗證、內容審核、檢舉機制、客服與平台治理、即時名額鎖定與併發控制。
