# Case Study Notes — Volleyball Hub

這份筆記是給看作品集的人看的，說明這個專案在解決什麼問題、怎麼做的決定、以及哪些地方是刻意留白。技術細節見 [PRODUCT_DECISIONS.md](PRODUCT_DECISIONS.md) 跟 [PRODUCT_LIMITATIONS.md](PRODUCT_LIMITATIONS.md)，這裡談的是產品層面的思路。

## 問題是什麼

排球圈子裡揪團、找臨打的方式大多還停留在 Line 群組跟社群貼文——資訊零散、格式不一，常常要私訊主辦方才知道場地在哪裡、程度限制多嚴格、還缺不缺人。等真的到了現場，才發現自己報名的那場其實是六人制競技隊，跟自己想找的休閒臨打完全不是一回事。

一般的活動報名平台（像是把羽球、跑步、桌遊都塞進同一套樣板的那種）沒有真的解決這個問題，因為它們的欄位是為「泛用活動」設計的：類型、時間、地點、價格。排球玩家真正在意的是網高、球制、場地材質、缺什麼位置——這些資訊如果沒有變成產品裡的一級公民，使用者永遠得靠額外溝通才能確認。

## 這個原型想證明什麼

這是一個作品集案例，目標是展示產品設計跟前端工程如何搭配解決一個具體、垂直的問題，而不是展示「我能做出多少功能」。所以整個設計圍繞幾個具體任務：

1. 讓篩選條件貼近真正的排球決策（網高、球制、位置缺人），而不是套殼泛用平台的欄位。
2. 在使用者投入時間報名之前，就讓他們看到夠不夠資訊做決定。
3. 明確區分「系統確定的事」跟「系統不確定、需要你自己確認的事」——條件比對、資訊完整度、位置偏好，每一個都刻意避免看起來比實際更肯定。
4. 在沒有後端的前提下，仍然把每個功能做到「跟真的一樣」的程度：報名驗證邏輯集中、狀態判斷一致、時區處理正確、localStorage 有版本化 migration——這些是使用者看不到、但決定一個原型是不是「玩具等級」還是「產品等級」的地方。

## 幾個關鍵設計

**位置缺人視覺化**：不是做一個花俏的即時看板，而是老實地把主辦方填寫的缺人資訊，用簡化的場地圖＋文字清單呈現，並清楚寫明這是示範資料不是即時名單。與其做一個看起來很厲害但背後是假資料的即時系統，不如做一個誠實、但確實有用的靜態呈現。

**快速加入，但還是要確認**：這個功能一開始的直覺做法是「一鍵報名」，但那等於讓系統代替使用者做一個有實際後果的決定。改成跳出確認視窗、而且跟一般報名共用完全相同的驗證邏輯，是為了不讓「方便」變成「繞過規則的後門」。

**篩選硬性、比對軟性**：篩選決定看不看得到，條件比對解釋看到的東西跟你要的差多少——這兩件事以前被混在一起做，拆開之後畫面反而更清楚，因為每個區塊都只回答一個問題。

**資訊完整度不做分數**：分數看起來精確，但這裡背後其實就是數有幾個欄位是空的。與其包裝成一個假裝有公信力的數字，不如老實地說「缺什麼」，並區分哪些缺漏真的重要（地址、聯絡方式）、哪些只是細節（設備清單）。

## 刻意的取捨

這個專案花了不少篇幅在「決定不做什麼」，這些決定本身也是設計的一部分：

- **不做付款、聊天、真人評論**：沒有後端支撐的這些功能，做出來只會是好看的假貨，比不做更傷產品的可信度。
- **已儲存的探索條件不承諾通知**：這是最容易被誤會成「訂閱」的功能，選擇把它縮回它字面上能做到的範圍，而不是暗示一個做不到的承諾。
- **活動比較上限訂在 3**：不是技術限制，是判斷「使用者一次能有效比較的量」，超過這個數字，介面複雜度上升的速度會比資訊價值快。
- **快速加入、資訊完整度都刻意避免看起來比實際更肯定**：這個原型裡沒有任何地方會讓使用者誤以為「系統幫我確認過了」，凡是系統無法保證的事，都用文字明確寫出「這只是偏好」「這是主辦方填寫的資料」。

## 這個案例展示的能力

橫跨產品設計與前端工程的判斷力：知道什麼時候該把一個通用平台的樣板改造成真正貼合垂直領域的產品；知道怎麼在沒有後端的限制下，仍然把商業邏輯（驗證、狀態判斷、資料一致性）寫得像正式產品一樣嚴謹；也知道什麼時候該誠實地在介面上寫「這是示範資料」，而不是用視覺設計掩蓋一個原型的真實邊界。
