# Product Limitations

Volleyball Hub 是一個**前端高擬真原型**，用來展示產品與互動設計，不是正式上線的服務。這份文件記錄目前架構的真實邊界，以及正式產品需要補上的能力——目的是讓看這個作品集案例的人知道：哪些是已經做出來的真實互動，哪些是刻意排除、留給未來版本的範圍。

## 核心原則：前端隱藏入口不等於真正的權限控制

這個原型裡，你看不到付款方式、交易紀錄、帳號安全等入口，是因為它們在設計階段就被**移出產品介面**，而不是用 CSS 藏起來、或用一個假的「權限不足」訊息擋著。這個區別很重要：

- 前端條件式渲染（例如 `{isAdmin && <Button/>}`）只能決定「畫面上看不看得到」，**擋不住任何直接呼叫 API 的人**。
- 正式的權限控制必須發生在伺服器端：每一次請求都要重新驗證這個使用者、這個角色，有沒有權限做這件事。
- 目前這個專案沒有 API、沒有伺服器，所以嚴格來說「權限控制」這件事根本還不存在——不是做得不夠嚴謹，是這一層完全還沒開始蓋。

## 目前這個原型「有」的東西

- React 18 + React Router 的前端路由與元件結構，搜尋／篩選／排序／分類檢視同步到網址列（`useSearchParams`）
- localStorage 模擬的資料層：活動資料、報名紀錄、篩選偏好、收藏、瀏覽歷史、個人資料設定、活動比較清單、已儲存的探索條件，並具備版本化 migration（`src/services/storageMigration.js`，目前版本 4）
- 集中管理的商業規則：`src/utils/bookingValidation.js`（表單與名額驗證）、`src/services/registrationService.js`（報名／候補／取消的「先驗證再寫入」決策，快速加入與一般報名共用）、`src/utils/eventStatus.js`（活動狀態統一判斷，避免每個頁面各自寫一套 full/cancelled/completed 邏輯）、`src/utils/informationQuality.js`（資訊完整度判斷）、`src/utils/alternativeFilters.js`（可替代篩選建議，每個建議都經過真實計算才會顯示）
- 純前端可以誠實完成的互動：搜尋、篩選、條件比對說明、報名表單（含防重複報名／候補、隊伍人數驗證、位置偏好）、快速加入、候補、取消與退款政策說明（文字說明，不是真的退款）、活動比較、已儲存的探索條件、收藏、瀏覽歷史、.ics 行事曆匯出、Web Share API 分享、統一 Toast 提示

## 目前這個原型「沒有」、正式產品需要補上的能力

### 身分與權限
- **Authentication**（登入身分驗證）——目前任何人都是同一個「訪客」，沒有真的登入
- **Authorization**（權限驗證）——沒有伺服器端的角色檢查
- 會員／主辦方／管理員三種角色權限模型
- API 層級的權限驗證（不是前端隱藏按鈕就叫做權限控制）

### 資料與交易
- 正式資料庫（目前是瀏覽器 localStorage，換裝置、換瀏覽器、清資料就會消失）
- 資料庫交易（transaction）與**即時名額鎖定**——目前兩個分頁同時搶最後一個名額，兩邊都會「成功報名」，因為完全沒有伺服器仲裁
- **Idempotency（冪等性）**——`registrationService.js` 在寫入前會先驗證（防止重複報名／重複候補、隊伍人數超額），驗證通過後才會「同時」更新活動與報名兩筆資料，但這只是應用層的先驗證再寫入，不是資料庫等級的原子交易；網路中斷或分頁關閉仍可能讓兩次 `localStorage.setItem` 只成功一半
- 資料保存期限規範、帳號刪除與個資刪除流程
- 操作紀錄（audit log）

### 搜尋與探索
- 目前 Explore 的搜尋、篩選、排序都是**在瀏覽器裡對記憶體中的活動陣列做線性掃描**，資料量小（15 筆種子資料）所以感覺不出效能問題，但這不是正式的搜尋架構
- 沒有後端搜尋引擎（例如全文索引、模糊比對、多語系斷詞），多關鍵字搜尋目前只是簡單的子字串 AND 比對
- 沒有分頁——正式產品的活動數量一多，Explore 需要伺服器端分頁或無限捲動，而不是把所有資料一次載入瀏覽器
- 沒有即時資料更新——另一個人建立、取消、或報滿一場活動，你的畫面不會自動更新，要重新整理才看得到
- 沒有多人併發控制——上面「資料與交易」提到的即時名額鎖定問題，本質上就是這裡缺少後端搜尋／資料層的具體案例之一

### 金流
- 線上付款、金流 Webhook
- 退款與對帳流程（目前的退款政策只是畫面上的文字說明，沒有任何金流串接）
- 交易紀錄（沒有真的交易，所以沒有交易紀錄）

### 通知
- 推播通知服務
- Email 通知服務
- 目前「通知偏好」這個功能沒有出現在 Profile 裡，因為沒有任何通知會真的發送——保留一個「開關」去控制一個不存在的功能，本身就是一種誤導

### 安全與內容治理
- HTTPS 傳輸加密（GitHub Pages 本身有 HTTPS，但應用層沒有額外加密邏輯）
- 密碼、雙重驗證、登入裝置管理——沒有帳號，所以沒有密碼
- 主辦方身分驗證、內容審核、檢舉機制
- 客服與平台治理流程
- 監控與錯誤追蹤（error tracking / observability）

### 位置需求與場地資訊——組織者填寫的示範資料，不是即時名單
- 活動詳情頁的「目前缺少位置」與活動卡片上的急徵徽章，資料來源永遠是 `positionsNeeded`——也就是主辦方建立／編輯活動時填寫的欄位，**不是根據誰報名了什麼位置即時計算出來的名單**。有人報名時選了「舉球」，不會讓 `positionsNeeded` 裡的舉球需求自動減少。
- 同理，網高、場地材質等欄位都是主辦方自行填寫，沒有場館資料庫可以核對正確性。
- RegisterModal 讓報名者選「希望參加的位置」，但這只是偏好，系統目前**不會**因為某個位置已經不缺人就擋掉選它的人——比較嚴格的「位置額滿就不能再選」規則明確留給未來版本（見下方 Roadmap 對應）。

### 比較（Compare）——瀏覽器本地清單，不是伺服器端收藏
- 活動比較清單（`vh-compare`）只存在目前瀏覽器的 localStorage，最多 3 場，換裝置或清除資料就會消失，沒有跨裝置同步。
- 比較頁面顯示的所有欄位都是活動當下的資料快照式讀取（每次進入頁面重新讀取），不是即時訂閱——如果活動在另一個分頁被取消或修改，除非重新整理，否則比較頁不會自動更新。

### 已儲存的探索條件——只是條件，不是訂閱
- 「已儲存的探索條件」（`vh-saved-searches`）只會記住篩選組合與排序方式，**不會**、也**無法**在有新活動符合條件時通知你——目前沒有任何背景排程或推播機制能做到這件事。這一點在儲存與列表畫面都刻意寫得很明白，避免讓人誤以為這是一個訂閱功能。
- 同一個瀏覽器最多只能存 5 組，超過需要先刪除才能再存；資料格式若毀損，會直接被視為空清單，不會嘗試部分修復。

### 資訊完整度——一種檢查，不是信任評分
- `getEventInformationQuality()` 只回傳三種狀態（資訊完整／部分資訊未提供／尚缺重要資訊）與缺少的欄位清單，**沒有分數、沒有百分比**，未來也不應該加上——分數會製造一種「這場活動比較可信」的錯覺，但這個原型完全無法驗證主辦方填寫的任何欄位是否屬實。

### 快速加入——瀏覽器記住的資料，不是帳號
- 快速加入使用的姓名、電話、常用位置全部來自 Profile 的 localStorage，**不是**一個真正登入的帳號在背後驗證身分；同一個瀏覽器换人使用，快速加入會直接沿用上一個人填寫的資料。
- 快速加入與一般報名共用同一套 `planRegistration`／`registrationService` 驗證邏輯，這保證了重複報名、候補、人數上限等規則不會被繞過，但也代表快速加入沒有比一般報名多任何額外的防偽或身分確認能力。

### 建立活動精靈——場地資料為示範，不是真的預約
- 4 步驟建立活動精靈裡的場館清單（評分、租金、地址）全部是寫死的示範資料，沒有串接任何真實場館系統；「建立活動」這個動作只會把資料寫進瀏覽器的 localStorage，**不會**產生任何真實的場地預約或費用扣款。
