# Product Limitations

Volleyball Hub 是一個**前端高擬真原型**，用來展示產品與互動設計，不是正式上線的服務。這份文件記錄目前架構的真實邊界，以及正式產品需要補上的能力——目的是讓看這個作品集案例的人知道：哪些是已經做出來的真實互動，哪些是刻意排除、留給未來版本的範圍。

## 核心原則：前端隱藏入口不等於真正的權限控制

這個原型裡，你看不到付款方式、交易紀錄、帳號安全等入口，是因為它們在設計階段就被**移出產品介面**，而不是用 CSS 藏起來、或用一個假的「權限不足」訊息擋著。這個區別很重要：

- 前端條件式渲染（例如 `{isAdmin && <Button/>}`）只能決定「畫面上看不看得到」，**擋不住任何直接呼叫 API 的人**。
- 正式的權限控制必須發生在伺服器端：每一次請求都要重新驗證這個使用者、這個角色，有沒有權限做這件事。
- 目前這個專案沒有 API、沒有伺服器，所以嚴格來說「權限控制」這件事根本還不存在——不是做得不夠嚴謹，是這一層完全還沒開始蓋。

## 目前這個原型「有」的東西

- React 18 + React Router 的前端路由與元件結構
- localStorage 模擬的資料層：報名紀錄、篩選偏好、收藏、瀏覽歷史、個人資料設定
- 純前端可以誠實完成的互動：篩選、條件比對說明、報名表單、候補、取消與退款政策說明（文字說明，不是真的退款）、收藏、瀏覽歷史、.ics 行事曆匯出、Web Share API 分享

## 目前這個原型「沒有」、正式產品需要補上的能力

### 身分與權限
- **Authentication**（登入身分驗證）——目前任何人都是同一個「訪客」，沒有真的登入
- **Authorization**（權限驗證）——沒有伺服器端的角色檢查
- 會員／主辦方／管理員三種角色權限模型
- API 層級的權限驗證（不是前端隱藏按鈕就叫做權限控制）

### 資料與交易
- 正式資料庫（目前是瀏覽器 localStorage，換裝置、換瀏覽器、清資料就會消失）
- 資料庫交易（transaction）與**即時名額鎖定**——目前兩個分頁同時搶最後一個名額，兩邊都會「成功報名」，因為完全沒有伺服器仲裁
- 資料保存期限規範、帳號刪除與個資刪除流程
- 操作紀錄（audit log）

### 金流
- 線上付款、金流 Webhook
- 退款與對帳流程（目前的退款政策只是畫面上的文字說明，沒有任何金流串接）
- 交易紀錄（沒有真的交易，所以沒有交易紀錄）

### 通知
- 推播通知服務
- Email 通知服務
- 目前「通知偏好」這個功能沒有出現在 Profile 裡，因為沒有任何通知會真的發送——保留一個「開關」去控制一個不存在的功能，本身就是一種誤導

### 安全與內容治理
- HTTPS 傳輸加密（GitHub Pages 本身有 HTTPS，但應用層沒有額外加密邏輯）
- 密碼、雙重驗證、登入裝置管理——沒有帳號，所以沒有密碼
- 主辦方身分驗證、內容審核、檢舉機制
- 客服與平台治理流程
- 監控與錯誤追蹤（error tracking / observability）
